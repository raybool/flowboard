# FB-006.1 — Архитектура совместной работы и истории активности

**Статус:** Design only / CRITICAL
**Следующий этап:** FB-006.2 — Prisma Models & Migrations
**Область:** TasksModule, ProjectsModule, Prisma/PostgreSQL, Workspace RBAC

## 1. Итоговые решения

1. Все новые сущности получают `workspaceId`; связи `TaskComment` и `TaskActivity` с задачей, а `TaskLabel` с задачей и меткой используют составные workspace-scoped foreign keys.
2. Комментарии — плоские, с soft delete и редактированием без отдельной таблицы ревизий в MVP. После удаления тела комментария API отдаёт tombstone, а не исходный текст.
3. Автор комментария и actor события — независимые от membership. В строке сохраняется UUID пользователя и короткий display-name snapshot; при удалении пользователя UUID обнуляется, snapshot остаётся.
4. Имена меток уникальны без учёта регистра внутри workspace через отдельное нормализованное поле `nameKey`. Цвет — только `#RRGGBB`.
5. MEMBER может назначать/снимать метки только с задач, которыми владеет по действующей Task ownership policy: creator или текущий assignee. OWNER/ADMIN могут работать с любой задачей workspace.
6. TaskActivity — продуктовая read-only история, не Security Audit Log и не MCP Audit Log. Запись создаётся тем же Prisma transaction client, что и бизнес-изменение.
7. `ActivityWriterService` экспортируется из независимого `TaskActivityModule`. `TasksModule` импортирует только этот модуль; Collaboration-модули не импортируются TasksModule и валидируют task/project через Prisma с составными условиями.
8. Для P2034 используется существующий `runSerializableTransaction`: повторяется весь callback, включая activity insert. Отдельный event bus, брокер, realtime и outbox в MVP не добавляются.

## 2. Контекст текущего репозитория

Проверены только релевантные источники:

- `apps/api/prisma/schema.prisma`: `Task` уже содержит `workspaceId`, `projectId`, `creatorId`, `assigneeMemberId`, а `Project` и `WorkspaceMember` имеют уникальные пары для составных ссылок.
- `apps/api/src/modules/tasks/tasks.service.ts`: create/update/status/assign/archive используют `runSerializableTransaction`; MEMBER может менять задачу, если является creator или assignee, а assignment для MEMBER ограничен собой.
- `apps/api/src/modules/projects/projects.service.ts`: manager policy — OWNER/ADMIN; архив проекта блокирует task writes.
- `apps/api/src/modules/workspaces/workspace-members.service.ts` и `workspace-roles.guard.ts`: guard проверяет workspace membership/role, но write-сервисы повторно проверяют membership внутри транзакции.
- `apps/api/src/common/pagination.ts`: opaque Base64URL cursor `{ createdAt, id }`, сортировка `createdAt DESC, id DESC`.
- `apps/api/src/main.ts`: `ValidationPipe` включает `transform`, `whitelist` и `forbidNonWhitelisted`.
- `apps/api/src/database/serializable-transaction.ts`: retry только для Prisma `P2034`, повторяется полный callback, после исчерпания попыток возвращается generic 503.

MCP Task Context FB-005 не содержит handoff или freshness records. Поэтому использован явно зафиксированный `MCP unavailable — repository fallback`; выводы проверены по текущим исходникам и Git state. `context.search` и `context.update_task_context` не были доступны в опубликованных MCP-инструментах текущего сеанса.

## 3. Границы и схема компонентов

Целевой dependency graph:

```text
AppModule
├── WorkspacesModule
├── ProjectsModule ────────> WorkspacesModule, DatabaseModule
├── TasksModule ───────────> WorkspacesModule, DatabaseModule, TaskActivityModule
├── TaskCommentsModule ────> WorkspacesModule, DatabaseModule, TaskActivityModule
├── LabelsModule ──────────> WorkspacesModule, DatabaseModule, TaskActivityModule
└── TaskActivityModule ────> DatabaseModule, WorkspacesModule (reader/controller)
                            └── ActivityWriterService (tx-only writer)
```

Правила зависимостей:

- `TaskActivityModule` не импортирует `TasksModule`; writer принимает `Prisma.TransactionClient` и не выполняет root-client запросов в callback.
- `TaskCommentsModule` и `LabelsModule` не импортируют `TasksModule`, чтобы не создать цикл `TasksModule ↔ Collaboration`. Проверка task/project и ownership остаётся в каждом use case через Prisma с составными условиями либо в будущем выделяется в небольшую access-policy abstraction без импорта модулей друг в друга.
- `TaskActivityController` отвечает только за чтение. `ActivityWriterService` не должен быть доступен HTTP-контроллеру как write endpoint.
- `ProjectsModule` не знает о collaboration-модулях. Архивация проекта сохраняет связанные rows; task writes после архивации блокируются по существующему правилу.

Транзакционная схема write use case:

```text
JWT user.id
  → guard membership/role (ранняя проверка)
  → service: Serializable transaction
       → повторная membership/ownership проверка через tx.workspaceMember
       → scoped target lookup (workspace + project + task/label/comment)
       → business mutation
       → ActivityWriterService.write(tx, event)
       → commit
  ↺ P2034: повторить весь callback; результат первой попытки discarded
```

## 4. Инварианты workspace isolation

Для каждого use case обязательны все проверки ниже:

- `workspaceId` берётся только из route и JWT membership, не из body; `authorId`, `actorId` и `deletedById` берутся из `AuthUser.id`/membership, никогда не доверяются DTO.
- Task lookup использует `{ workspaceId, projectId, id: taskId }`; одного `taskId` недостаточно. Project lookup использует `{ workspaceId, id: projectId }`.
- Comment lookup использует `{ workspaceId, taskId, id: commentId }`. Label lookup — `{ workspaceId, id: labelId }`.
- Связь task/label вставляется только после получения обеих записей в одном workspace; составные FK дополнительно блокируют cross-workspace substitution на уровне PostgreSQL.
- Read queries либо сначала вызывают `requireMembership`, либо содержат relation filter `workspace.members.some(userId)`; write queries повторяют проверку внутри serializable transaction.
- Ошибка для чужих workspace/task/comment/label — `NotFoundException`, чтобы не раскрывать наличие чужого ID. Недостаток роли для уже найденного собственного ресурса — `ForbiddenException`.
- DTO имеют только бизнес-поля; global `forbidNonWhitelisted` сохраняется. Никаких `workspaceId`, `authorId`, `actorId`, `createdAt`, `updatedAt`, `deletedAt`, `payload` в client DTO.
- При отзыве membership конкурентная write-транзакция либо видит отсутствие membership и отклоняется, либо сериализуется до/после revoke. Операция, уже committed до revoke, считается допустимой; последующие операции запрещены.

## 5. Task Comments

### 5.1 Решения MVP

| Вопрос                          | Решение                                                                                                                                                                                                                |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Автор после удаления membership | Сохранять attribution: `authorId` остаётся, membership не является FK комментария; display-name snapshot сохраняется. Удаление membership не удаляет комментарий.                                                      |
| Удаление                        | Soft delete. `deletedAt` и `deletedById` сохраняются, `content` редактируется в `NULL` в рамках той же транзакции. В API виден tombstone. Restore endpoint отсутствует.                                                |
| История редактирования          | Отдельные revisions не входят в MVP. `COMMENT_UPDATED` фиксирует факт и метаданные изменения; полноценные версии — отдельный future work.                                                                              |
| Вложенность                     | Нет parent/reply в MVP; комментарии плоские.                                                                                                                                                                           |
| Markdown                        | Хранить исходный Markdown как plain text, разрешить ограниченный CommonMark subset на клиенте/рендерере и санитизировать HTML на сервере/границе отображения. Raw HTML и URL schemes `javascript:`, `data:` запрещены. |
| Максимум                        | 10 000 Unicode characters, после trim; пустая строка запрещена. PostgreSQL CHECK и DTO должны совпадать.                                                                                                               |
| Архивная задача                 | Читать комментарии можно. Создание и редактирование блокируются с `409 Task is archived`; OWNER/ADMIN могут soft-delete для модерации.                                                                                 |
| Удаление пользователя           | `authorId`, `deletedById` становятся `NULL` через `ON DELETE SET NULL`; snapshots остаются. Политика не требует запрета удаления пользователя.                                                                         |

Удалённый комментарий не должен возвращать исходный текст ни MEMBER, ни модератору через обычный API. Это снижает риск повторного раскрытия удалённого конфиденциального содержимого. Если в будущем понадобится legal hold, он должен быть отдельным privileged workflow.

### 5.2 DTO и response shape

```text
CreateTaskCommentDto / UpdateTaskCommentDto
  content: string, 1..10000, trimmed

TaskCommentResponse
  id, workspaceId, taskId,
  author: { id: string | null, displayName: string },
  content: string | null,
  deletedAt: string | null,
  createdAt, updatedAt
```

`author.displayName` — snapshot, а не произвольное значение из запроса. Для deleted user допустим нейтральный display value, но нельзя подменять attribution request body.

### 5.3 Pagination

GET использует существующий cursor `{ createdAt, id }`, `limit` 1..100, сортировку `createdAt DESC, id DESC` и индекс `workspaceId, taskId, createdAt, id`. Список включает tombstones для стабильной временной линии; тела удалённых комментариев не возвращаются.

## 6. Labels и TaskLabel

### 6.1 Решения MVP

- Label живёт на уровне workspace.
- `name` уникален без учёта регистра и пробелов: приложение вычисляет `nameKey = NFC(trim(name)).casefold()` и сохраняет display `name` отдельно. Уникальность — `workspaceId + nameKey`; это избегает зависимости от `citext` extension и функциональных индексов.
- `name` — 1..50 Unicode characters; `nameKey` не пустой. `color` хранится в каноническом uppercase формате `#RRGGBB`; alpha, short hex и CSS names запрещены.
- Создавать, менять и удалять labels могут только OWNER/ADMIN. Назначать и снимать label может OWNER/ADMIN либо MEMBER, который является creator/current assignee задачи согласно существующей ownership policy.
- Удаление label — hard delete с `TaskLabel ON DELETE CASCADE`. Это конфигурационная сущность; исторические `LABEL_ADDED/LABEL_REMOVED` rows сохраняют snapshot имени и цвета и не ссылаются обратно на живой label.
- Повторный `PUT` связи — no-op без повторного activity event. Повторный `DELETE` отсутствующей связи — idempotent 204 после проверки workspace-scoped task и label.
- Фильтр задач: `labelIds` — повторяемый query parameter, максимум 20 UUID, AND semantics (задача должна иметь все выбранные labels). OR semantics можно добавить отдельно, не меняя storage.

### 6.2 Индексы

`TaskLabel` получает:

- primary key `(workspaceId, taskId, labelId)` — запрет дублей и tenant key;
- индекс `(workspaceId, labelId, taskId)` — фильтр задач по label;
- индекс `(workspaceId, taskId, labelId)` — список labels задачи и проверка связи.

`Label` получает `(workspaceId, createdAt, id)` для cursor list и unique `(workspaceId, nameKey)`.

### 6.3 Связь с activity

При фактическом добавлении/снятии связи создаётся `LABEL_ADDED`/`LABEL_REMOVED`. Payload содержит snapshot `{ labelId, name, color }`, поэтому история не ломается после hard delete label. Удаление label с множеством задач — отдельная manager transaction; если в MVP не нужен fan-out activity, допускается один product-level event вне TaskActivity только после отдельного решения. Базовый вариант для FB-006.4 — писать per-task removal events в той же transaction, с ограничением на размер операции и тестом rollback.

## 7. Activity History

### 7.1 MVP event set

В MVP реализуются все перечисленные продуктовые события:

```text
TASK_CREATED
TASK_UPDATED              // title и/или description; status/priority/assignee отдельно
TASK_STATUS_CHANGED
TASK_PRIORITY_CHANGED
TASK_ASSIGNEE_CHANGED
TASK_ARCHIVED
COMMENT_CREATED
COMMENT_UPDATED
COMMENT_DELETED
LABEL_ADDED
LABEL_REMOVED
```

Отложены: project changes, membership/role changes, comments/revisions, bulk operations, automation/system events и security events. Они не должны быть замаскированы под `TASK_UPDATED`.

### 7.2 Payload contract

`payload` — server-generated JSON object. Клиент не присылает payload и не может выбрать event type. Минимальный envelope:

```json
{
  "schemaVersion": 1,
  "entity": "task",
  "changes": {
    "status": { "from": "TODO", "to": "IN_PROGRESS" }
  },
  "snapshot": {
    "taskId": "uuid",
    "taskNumber": "FLOW-42"
  }
}
```

Правила:

- Task field changes используют `changes[field].from/to`; `null` означает отсутствие значения. `TASK_UPDATED` не дублирует status/priority/assignee events.
- Для изменения `description` `TASK_UPDATED` использует только `changes.descriptionChanged: true`; значения `from/to`, фрагменты и обратимо закодированное содержимое description запрещены.
- Assignee values — `{ memberId, userId, displayName } | null`; snapshot нужен для истории после membership/user deletion.
- Label events — `{ labelId, name, color }` в snapshot.
- Comment events — `{ commentId, contentLength, contentHash? }`; raw body и предыдущий body в activity не копируются. `COMMENT_UPDATED` описывает факт редактирования, а не является revision store.
- `TASK_CREATED` содержит безопасный начальный snapshot без полного description, если description может содержать конфиденциальные данные. В payload не включаются password, tokens, email без необходимости и произвольные DTO поля.
- `schemaVersion` находится и в envelope, и в колонке `eventVersion`/`version` row; изменение схемы payload требует новой версии и backward-compatible reader.
- `correlationId` группирует несколько событий одной операции; `requestId` связывает HTTP request. Оба генерируются/проставляются сервером и не являются dedupe key в MVP.

### 7.3 Транзакционная стратегия и retry

`ActivityWriterService.write(transaction, input)` вызывается после успешной domain mutation и до выхода из `runSerializableTransaction` callback. Для create/update/status/assign/archive tasks, comment writes и label relation writes граница одна:

```text
require membership/role in tx
→ load scoped records in tx
→ compare old/new state
→ update/insert/delete domain row
→ insert task_activity
→ commit
```

При rollback ни domain row, ни event не остаются. При P2034 `runSerializableTransaction` повторяет весь callback на новом transaction client; первая запись activity откатывается PostgreSQL, поэтому retry не создаёт duplicate event. Нельзя:

- писать activity через `this.prisma` внутри callback;
- отправлять notification/realtime/webhook до commit;
- генерировать и сохранять event вне callback;
- считать `requestId` достаточным для защиты от повторной клиентской отправки.

Повторная доставка одного и того же HTTP запроса после уже успешного commit — отдельная проблема; idempotency keys могут быть добавлены позже и не являются частью FB-006.1.

### 7.4 Хранение actor и жизненный цикл

Actor определяется только из JWT `AuthUser.id` и повторно проверяется как workspace member в transaction. `actorId` nullable с `ON DELETE SET NULL`, `actorDisplayName` snapshot сохраняется. Это не превращает activity в immutable security audit: Activity отражает продуктовые изменения task.

TaskActivity не редактируется обычным REST API. В миграции следует запретить application-level UPDATE/DELETE и добавить DB-level защиту от UPDATE; parent workspace/task cascade должен оставаться возможным для удаления tenant/domain data. Политику прямого SQL purge должен контролировать отдельный административный процесс, не API.

### 7.5 Outbox extension point

MVP не вводит outbox. `ActivityWriterService` — единственная точка записи — оставляет место для будущего `OutboxWriter` в той же transaction. После добавления outbox dedupe key должен быть уникален для committed domain operation; обычный `TaskActivity.id` нельзя использовать как внешний delivery id до commit.

## 8. Предварительная Prisma data model

Ниже контракт для FB-006.2; текущая `schema.prisma` этим документом не изменялась. Поля `createdAt`/`updatedAt` используют существующую naming convention с snake_case mapping только там, где она уже применяется.

```prisma
enum TaskActivityType {
  TASK_CREATED
  TASK_UPDATED
  TASK_STATUS_CHANGED
  TASK_PRIORITY_CHANGED
  TASK_ASSIGNEE_CHANGED
  TASK_ARCHIVED
  COMMENT_CREATED
  COMMENT_UPDATED
  COMMENT_DELETED
  LABEL_ADDED
  LABEL_REMOVED
}

model TaskComment {
  id                 String    @id @default(uuid())
  workspaceId        String    @map("workspace_id")
  taskId             String    @map("task_id")
  authorId           String?   @map("author_id")
  authorDisplayName  String    @map("author_display_name")
  content            String?
  deletedAt          DateTime? @map("deleted_at")
  deletedById        String?   @map("deleted_by_id")
  createdAt          DateTime  @default(now()) @map("created_at")
  updatedAt          DateTime  @updatedAt @map("updated_at")

  task       Task  @relation(fields: [workspaceId, taskId], references: [workspaceId, id], onDelete: Cascade)
  author     User? @relation("TaskCommentAuthor", fields: [authorId], references: [id], onDelete: SetNull)
  deletedBy  User? @relation("TaskCommentDeletedBy", fields: [deletedById], references: [id], onDelete: SetNull)

  @@unique([workspaceId, id])
  @@index([workspaceId, taskId, createdAt, id])
  @@index([workspaceId, authorId, createdAt, id])
  @@map("task_comments")
}

model Label {
  id          String   @id @default(uuid())
  workspaceId String   @map("workspace_id")
  name        String
  nameKey     String   @map("name_key")
  color       String
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @updatedAt @map("updated_at")

  workspace Workspace  @relation(fields: [workspaceId], references: [id], onDelete: Cascade)
  tasks     TaskLabel[]

  @@unique([workspaceId, id])
  @@unique([workspaceId, nameKey])
  @@index([workspaceId, createdAt, id])
  @@map("labels")
}

model TaskLabel {
  workspaceId String @map("workspace_id")
  taskId      String @map("task_id")
  labelId     String @map("label_id")

  task  Task  @relation(fields: [workspaceId, taskId], references: [workspaceId, id], onDelete: Cascade)
  label Label @relation(fields: [workspaceId, labelId], references: [workspaceId, id], onDelete: Cascade)

  @@id([workspaceId, taskId, labelId])
  @@index([workspaceId, labelId, taskId])
  @@index([workspaceId, taskId, labelId])
  @@map("task_labels")
}

model TaskActivity {
  id                 String           @id @default(uuid())
  workspaceId        String           @map("workspace_id")
  taskId             String           @map("task_id")
  actorId            String?          @map("actor_id")
  actorDisplayName   String?          @map("actor_display_name")
  type               TaskActivityType
  eventVersion       Int              @default(1) @map("event_version")
  payload            Json
  correlationId      String?          @map("correlation_id")
  requestId          String?          @map("request_id")
  createdAt          DateTime         @default(now()) @map("created_at")

  task  Task  @relation(fields: [workspaceId, taskId], references: [workspaceId, id], onDelete: Cascade)
  actor User? @relation(fields: [actorId], references: [id], onDelete: SetNull)

  @@unique([workspaceId, id])
  @@index([workspaceId, taskId, createdAt, id])
  @@index([workspaceId, actorId, createdAt, id])
  @@map("task_activities")
}
```

Обязательные relation additions в существующих моделях:

```prisma
// User
taskCommentAuthors      TaskComment[]  @relation("TaskCommentAuthor")
taskCommentDeletions    TaskComment[]  @relation("TaskCommentDeletedBy")
taskActivities          TaskActivity[]

// Workspace
labels                  Label[]

// Task
comments                TaskComment[]
labels                  TaskLabel[]
activities              TaskActivity[]
```

Примечания к Prisma/PostgreSQL:

- Составные relations требуют уже существующие `@@unique([workspaceId, id])` на `Project`, `WorkspaceMember` и `Task`/новых сущностях. Перед миграцией FB-006.2 должен явно подтвердить/добавить `@@unique([workspaceId, id])`, иначе Prisma/PostgreSQL composite FK не будет валиден.
- Prisma не выражает immutable-row policy, `nameKey` canonicalization, color regex, content length и JSON payload shape как полноценный API contract. FB-006.2 добавляет PostgreSQL CHECK constraints и миграционные ограничения.
- `TaskActivity.payload` — PostgreSQL `jsonb` через Prisma `Json`; JSON schema проверяется writer/service tests. CHECK должен минимум требовать object и `schemaVersion`.
- `TaskActivity` не получает `updatedAt`: строка immutable по продуктовой модели.
- `TaskComment.content` nullable намеренно: soft delete превращает тело в tombstone. `deletedAt` — единственный признак удаления, не `content IS NULL`.
- На уровне FK: workspace deletion cascades labels/comments/activities/task labels through domain tree; task deletion cascades comments/task labels/activity; label deletion cascades task labels; user deletion sets author/actor/moderator IDs null; membership deletion не затрагивает comments/activity и не может удалить attribution.

## 9. REST API contract

Все пути ниже находятся под глобальным `/api/v1` и требуют Bearer auth. `:workspaceId`, `:projectId`, `:taskId`, `:commentId`, `:labelId` валидируются `ParseUUIDPipe`.

### Comments

```text
POST   /workspaces/:workspaceId/projects/:projectId/tasks/:taskId/comments
GET    /workspaces/:workspaceId/projects/:projectId/tasks/:taskId/comments?limit=50&cursor=...
PATCH  /workspaces/:workspaceId/projects/:projectId/tasks/:taskId/comments/:commentId
DELETE /workspaces/:workspaceId/projects/:projectId/tasks/:taskId/comments/:commentId
```

- POST: MEMBER/ADMIN/OWNER; body `{ content }`; 201; actor/author from JWT.
- GET: любой текущий workspace member; 200 `{ items, nextCursor }`; tombstones включены.
- PATCH: только author, пока comment не deleted и task не archived; manager не может редактировать чужой текст, только удалить; 200.
- DELETE: author либо OWNER/ADMIN; soft delete; 204. Для archived task доступна только manager moderation path.
- `commentId` всегда проверяется одновременно с workspace/task; нельзя принять comment из другой task даже при совпадающем UUID.

### Labels

```text
POST   /workspaces/:workspaceId/labels
GET    /workspaces/:workspaceId/labels?limit=50&cursor=...
PATCH  /workspaces/:workspaceId/labels/:labelId
DELETE /workspaces/:workspaceId/labels/:labelId

PUT    /workspaces/:workspaceId/projects/:projectId/tasks/:taskId/labels/:labelId
DELETE /workspaces/:workspaceId/projects/:projectId/tasks/:taskId/labels/:labelId
```

- POST/PATCH/DELETE label: OWNER/ADMIN; body create `{ name, color }`, update — оба поля optional, но после merge оба валидны; 201/200/204.
- GET: любой member; cursor order `createdAt DESC, id DESC`.
- PUT relation: OWNER/ADMIN или task owner; idempotent 204; duplicate relation не создаёт event.
- DELETE relation: OWNER/ADMIN или task owner; idempotent 204; фактическое снятие создаёт event.
- Task list получает `labelIds` filter в существующем task endpoint; это изменение контракта FB-006.4, не новый endpoint.

### Activity

```text
GET /workspaces/:workspaceId/projects/:projectId/tasks/:taskId/activity?limit=50&cursor=...
```

- 200 `{ items, nextCursor }`, newest first, opaque cursor.
- Только текущие workspace members; endpoint не принимает body и не имеет POST/PATCH/DELETE.
- Возвращать `actorId`/snapshot, `type`, `eventVersion`, `payload`, `createdAt`; не возвращать внутренние DB ошибки или лишние user fields.
- При archived task чтение разрешено членам workspace; history не удаляется при archive.

### HTTP error contract

Сохраняются существующие Nest semantics: `400` для invalid UUID/cursor/DTO, `401` для отсутствующего JWT, `403` для недостаточной роли/ownership, `404` для workspace-scoped отсутствующего ресурса, `409` для archived target и unique name conflict, `503` после exhausted P2034 retries.

| Операция                                      | OWNER | ADMIN | MEMBER |

| Читать комментарии своей workspace            |    Да |    Да |     Да |

## 11. Security и race-condition checklist

- **Cross-workspace IDOR:** route IDs и body IDs не являются доказательством принадлежности; составные FKs и scoped `findFirst`/`findUnique` обязательны.
- **Cross-project substitution:** task endpoint проверяет одновременно `workspaceId + projectId + taskId`; activity/comment/label relation не принимают только task UUID.
- **Foreign comment ID:** comment service проверяет comment через `(workspaceId, taskId, commentId)`, а не сначала по `id`.
- **Foreign label attach:** до PUT загружаются task/project и label в одном workspace; DB composite FK — второй барьер.
- **Чужое редактирование:** author match в transaction; manager может удалить, но не редактировать тело чужого комментария.
- **Actor spoofing:** DTO не содержит actor/author; writer получает actor из authenticated service argument.
- **Mass assignment:** DTO + global whitelist/forbid unknown; response mappers не отдают внутренние поля.
- **Removed membership:** comments/activity attribution сохраняются, но read/write permission требует текущего membership. Сервисы повторяют membership check внутри tx.
- **Concurrent revoke:** serializable transaction читает membership и target в том же callback; P2034 вызывает полный retry.
- **Payload leakage:** whitelist event fields, не сохранять full comment body/description/password/tokens; избегать email без требования продукта.
- **XSS/Markdown:** хранить plain Markdown, не доверять raw HTML, санитизировать rendered HTML, тестировать dangerous links/scripts.
- **Immutable activity:** нет REST writes; миграция ограничивает UPDATE/DELETE application role и добавляет DB CHECK/trigger policy, совместимую с parent cascade.
- **No-op transitions:** event создаётся только если значение реально изменилось. Это предотвращает шум и ложные `from == to` события.

## 12. Тестовая стратегия

Unit/DTO/controller tests должны проверять metadata, validation, ownership branches и отсутствие write endpoints для ActivityController. PostgreSQL integration tests обязательны для FK/unique/index behavior.

### Comments

- create/read с cursor pagination и стабильным `nextCursor`;
- edit author success; edit foreign author forbidden/not found;
- soft delete redacts content, returns tombstone, is idempotent only by explicit policy;
- OWNER/ADMIN moderation; MEMBER cannot delete foreign comment;
- archived task: read allowed, create/edit rejected, manager moderation allowed;
- membership removal/user deletion сохраняют attribution snapshot согласно FK policy;
- dangerous Markdown/HTML and max length validation.

### Labels

- `nameKey` uniqueness for `Bug`, `bug` and case variants;
- color/name CHECK constraints;
- cross-workspace label attach rejected both service-level and DB-level;
- duplicate PUT creates one row and one event;
- hard delete label cascades TaskLabel and preserves activity snapshots;
- task filtering by one/all selected labels uses expected indexes and no cross-workspace rows;
- MEMBER ownership matrix and manager catalog matrix.

### Activity

- each business mutation emits the correct event with previous/current values;
- no-op update emits no event;
- domain row and activity row commit/rollback together;
- a synthetic P2034 makes the full callback run twice and leaves one committed event;
- actor comes from JWT/service argument, not DTO;
- activity GET is read-only and workspace/project/task scoped;
- comment event payload contains metadata, not raw body;
- history remains readable after archive and actor user deletion.

### Concurrency

- simultaneous comment edits: serializable outcome is deterministic; no partial activity;
- simultaneous same-label PUT: one relation, one event;
- task mutation vs membership revoke: no write after revoke commit;
- concurrent task updates produce valid independent events with correct snapshots;
- label delete vs relation PUT returns a controlled conflict/not-found, never a cross-workspace link.

## 14. Риски и открытые вопросы

1. **Prisma composite FK support:** текущие patterns уже используются для Task→Project и Task→WorkspaceMember. FB-006.2 обязан сгенерировать client и проверить exact relation syntax, особенно несколько User relations и `SetNull`.
2. **Immutable history vs cascade:** прямые DELETE/UPDATE и parent cascade должны быть разделены на уровне DB policy. Нужна PostgreSQL integration test before accepting migration.
3. **Label delete fan-out:** удаление label с большим числом tasks может создать много `LABEL_REMOVED` events. MVP должен либо ограничить batch size, либо явно выбрать один aggregate event; это не должно приводить к частично удалённому catalog.
4. **Strict event ordering:** cursor `createdAt,id` даёт deterministic pagination, но не отдельный per-task sequence. Строгий causal sequence для realtime/analytics — future migration, не добавлять скрытый `MAX(sequence)+1` race.
5. **Comment revision/legal hold:** soft delete tombstone и metadata-only edit events подходят product history, но не заменяют compliance archive. Если появится требование восстановления или legal hold, нужна отдельная permission boundary.
6. **Client duplicate requests:** P2034 retry защищён transaction rollback; уже committed повторный HTTP POST может дать два легитимных комментария/события. Idempotency-Key — будущая capability.
7. **Knowledge handoff:** текущий MCP context server не предоставил `context.search`/`context.update_task_context` инструментов в сессии; handoff ниже нужно сохранить при первой доступной операции context update.
