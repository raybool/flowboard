# FB-006.10a — Legacy label name-key compatibility

## Runtime guard

`LabelsService.create` and `LabelsService.update` keep the existing Unicode
16.0.0 Default Case Folding algorithm and display names unchanged. Before the
mutation they acquire a transaction-scoped PostgreSQL row lock on the matching
`workspaces` row, read at most `MAX_LABEL_NAME_COMPATIBILITY_SCAN + 1` label IDs
from that workspace (including the current label during update), then perform a
separate bounded name scan that excludes the current label only for conflict
detection. Both reads and the write are in the same Serializable transaction,
and the existing P2034 retry wrapper retries the complete unit.

The limit is a fail-closed guard, not a correctness shortcut: workspaces over
the limit receive 503 until the backfill is completed. The temporary scans are
workspace-scoped and select only `id` or `id` and `name`; each is bounded by
`MAX_LABEL_NAME_COMPATIBILITY_SCAN + 1`. Remove this compatibility path after
the collision report is empty and the reviewed backfill has completed.

The workspace row lock is transaction-scoped, so different workspaces do not
block one another. It is used by both the runtime mutation and the backfill
procedure.

## Read-only collision report

Run the existing report first. It lists each workspace, normalized key, label
IDs, display names, and legacy keys. A non-empty report is a stop condition.
No label or `TaskLabel` row is deleted, renamed, or merged automatically.

```sh
pnpm --filter api labels:report-name-key-collisions
```

## Backfill contract

The backfill is dry-run by default and never runs automatically from deploy,
development startup, or tests:

```sh
pnpm --filter api labels:backfill-name-keys
```

After every reported collision has been resolved by an explicitly reviewed
rename/removal plan, create a database backup and run write mode with an
explicit backup file and confirmation:

```sh
pnpm --filter api labels:backfill-name-keys -- \
  --write --confirm --backup-file=/secure/path/labels-name-keys.json
```

Write mode locks the affected workspaces, re-reads all labels, rechecks
collisions, and updates only `labels.name_key` in one Serializable transaction.
Any error rolls back the transaction. Label IDs and `TaskLabel` relations are
not touched. The JSON backup contains the original label IDs, workspace IDs,
names, and name keys. Preserve it with the database backup; restore by
reviewed SQL in a transaction using `(workspace_id, id)` from that file, then
rerun the collision report and dry-run. Do not restore into a database whose
label set has changed without a fresh review.

The procedure is repeat-safe: a second dry-run reports zero changes after a
successful write, and a second write commits zero updates. Production and
development databases require an operator-selected `DATABASE_URL` and the
explicit write flags; no automatic backfill is performed.
